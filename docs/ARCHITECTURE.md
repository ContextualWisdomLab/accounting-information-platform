# Architecture

## Authority topology

```text
Operational systems         Metering Billing Platform
        |                              |
        +-------- economic facts ------+
                                       |
                            accounting_journal_proposal
                                       |
                                       v
                    Accounting Information Platform
                    - proposal intake and evidence
                    - policy and mapping resolution
                    - period and currency controls
                    - immutable journals and reversals
                    - trial balance and close
                    - financial reporting projections
                                       |
                          accounting_posting_receipt
                                       |
                  source reconciliation and audit evidence
```

## Bounded modules

| Module | Responsibility |
|---|---|
| `proposal_intake` | schema, source authority, idempotency, payload identity |
| `policy_resolution` | entity, book, period, currencies, account-role mapping |
| `journal_posting` | exact balance, immutable journal and lines, source lineage |
| `journal_reversal` | equal-and-opposite correction and replacement lineage |
| `trial_balance` | deterministic journal population aggregation |
| `close_control` | period states, hold queues, close and reopen governance |
| `reporting_projection` | versioned trial-balance and financial-statement views |
| `integration_outbox` | authoritative receipt and event publication after commit, plus append-only audit history of those same rows |

## Current implementation

`accounting_information_platform.core` is the reference implementation for proposal validation, policy checks, posting, reversal, and trial balance. It has no network or database dependency. `ingest_journal_proposal` reads the Billing-owned JSON contract field `proposal_status` and accepts only `validated` or `exported` before constructing a status-free `JournalProposal`. Line amounts stay canonical decimal strings; JSON numbers, missing line keys, non-integer `line_number` or `proposal_contract_version`, and Billing `retained_earnings` fail closed. `accept_journal_proposal` and `POST /journal-proposals` ingest a Billing proposal and return `accounting_posting_receipt`. `lookup_published_receipt` and `GET /posting-receipts?idempotency_key=` return that same persisted receipt for a later Billing read. `pull_validated_journal_proposals` and `accept_pulled_proposals` GET Billing #15 `validated` pages (body keys `journal_proposals` + `next_cursor` only; query `cursor`; default `page_limit` 50, maximum 100) and post through `accept_journal_proposal` without flipping Billing `proposal_status`. The pull document always includes `posting_receipts` and `rejected_proposals`; a stuck `next_cursor` or more than 20 pages is 422. `POST /billing-proposal-pulls` exposes that command. `accept_period_close` and `POST /period-closes` take optional body `period_status_code` (`soft_closed` or `hard_closed`; omit is `hard_closed`; empty or null is 422). Soft-close rejects ordinary posts, allows append-only reversal, and writes no snapshot; hard-close posts AIS closing entries that zero revenue and expense into `retained_earnings` 310100, then snapshots the book and rejects posts and reversals. `lookup_trial_balance` and `GET /trial-balances` return snapshot totals for a hard-closed period or live aggregation for an open or soft-closed period. Optional `balance_basis_code` is `unadjusted`, `adjusted`, or `post_close`; omit keeps today's live-or-snapshot keys. `unadjusted` sums posted lines through period end excluding adjusting lines and the AIS period-closing journal. `adjusted` includes adjusting journals and excludes that closing journal. Both live bases work after hard-close and do not read the snapshot. `post_close` returns the stored `trial_balance_snapshot` only and does not invent a post-close TB from live journals. Account-balance, rollforward, and financial-statement reads stay on their current live-vs-snapshot rules. `lookup_period_closes` and `GET /period-closes?legal_entity_reference=` list durable hard-close receipts from existing `trial_balance_snapshot` rows using the same close-receipt keys (`replayed` is false on the stored snapshot). Soft-close writes no snapshot, so the list does not invent soft-close history. Optional `fiscal_period_reference` and `period_status_code` (`soft_closed` | `hard_closed`) filter those stored rows (`page_limit` default 50, maximum 100, `next_cursor` on `snapshot_generated_at|snapshot_record_id`). Empty history returns `period_closes` []. `POST /period-closes` remains the close command. `accept_adjusting_journal` and `POST /journals` post one AIS-owned adjusting journal through the ordinary `PostgresPostingLedger` post tables and return the existing `accounting_posting_receipt`; lines carry statutory `chart_account_code` (not a Billing `account_role_code`), the period must be `open` or `soft_closed`, and `hard_closed` is 409. `lookup_posted_journal` and `GET /journals?idempotency_key=` or `GET /journals?journal_reference=` return one persisted journal and its lines, including an adjusting journal after accept; `lookup_period_journals` and `GET /journals?legal_entity_reference=&fiscal_period_reference=&book_reference=` list existing posted and reversing journals for that period (`page_limit` default 50, maximum 100, `next_cursor` on `accounting_date|journal_reference`). Optional `journal_source_code` is `billing`, `adjusting`, `period_closing`, or `reversal`; omit keeps today's keys. `adjusting` is journals whose lines have `account_role_code=adjusting`. `period_closing` is the AIS hard-close journal. `reversal` is the existing `journal_reversal` lineage. `billing` is the remaining posted journals. Single-journal GET by key or reference is unchanged. `lookup_journal_reversals` and `GET /journal-reversals?legal_entity_reference=` list existing `journal_reversal` rows for that tenant entity (`reversal_journal_reference`, `original_journal_reference`, `reversal_date` from the reversing journal `accounting_date`, `posted_at`, and stored `reversal_reason_code`); optional `original_journal_reference` and `fiscal_period_reference` filter those stored rows (`page_limit` default 50, maximum 100, `next_cursor` on `posted_at|journal_reference`). Empty history returns `journal_reversals` []. `POST /journal-reversals` remains the reverse command. `lookup_outbox_events` and `GET /outbox-events?event_type_code=` return unpublished `outbox_event` rows (`payload_reference` is the existing receipt, snapshot, or soft-close fiscal-period URN); `publish_outbox_event` and `POST /outbox-events/{outbox_event_id}/publish` set `published_at` on that tenant row. `lookup_audit_events` and `GET /audit-events` return the same tenant `outbox_event` rows whether or not `published_at` is set, reuse the outbox item keys plus `published_at`, and never mark publish; optional `event_type_code` filters `posting_receipt`, `period_close`, or `journal_reversal`, and paging reuses `created_at|outbox_event_id`. `lookup_fiscal_periods` and `GET /fiscal-periods?legal_entity_reference=` list existing `fiscal_period` rows for that tenant entity (`page_limit` default 50, maximum 100, `next_cursor` on `period_start_date|period_code`); single GET by `fiscal_period_reference` remains the period-status read. `lookup_account_ledger` and `GET /account-ledgers?legal_entity_reference=&chart_account_code=` return posted journal lines for one statutory chart account, optionally scoped by `fiscal_period_reference`, with exact `period_debit_total` / `period_credit_total` for the filtered scope. `lookup_account_balances` and `GET /account-balances?legal_entity_reference=&book_reference=&fiscal_period_reference=` return as-of chart-account balances (`chart_account_code`, `account_class_code`, unsigned debit/credit) from the hard-close `trial_balance_snapshot` when one exists, otherwise from live posted lines through period end. Optional `chart_account_code` keeps one account in the collection. Pages use `chart_account_code` order (`page_limit` default 50, maximum 100). Empty books return `account_balances` []. `lookup_account_rollforward` and `GET /account-rollforwards?legal_entity_reference=&book_reference=&fiscal_period_reference=&chart_account_code=` return opening + period = closing unsigned sides for one chart account. Opening is the prior hard-close snapshot when one exists, otherwise live activity before the scope start. Period activity includes adjusting journals and the AIS period-closing journal. Closing equals `GET /account-balances` for that account and period. Optional `statement_scope_code` is `period` or `year_to_date`; the document includes that key only for `year_to_date`. `lookup_receivable_aging` and `GET /receivable-agings?legal_entity_reference=&book_reference=&fiscal_period_reference=` return entity-level FIFO AR aging as of that period's end date (`current`, `days_31_60`, `days_61_90`, `days_over_90`, and `total_outstanding_amount`). Default `chart_account_code` is the catalog `accounts_receivable` account. Credit lines, including a Billing #51 collection write-off credit on 110100, consume the oldest open debit first so the aging total drops by that write-off amount and still equals the AR account-balance net. Excess AR credit does not create a negative bucket sum; the document then includes `unapplied_credit_amount` and omits that key when there is no excess. Adjusting journals that touch AR are included; the AIS period-closing journal is excluded. After hard-close the total still equals the AR account-balance net. This slice does not add `party_reference`. `lookup_payable_aging` and `GET /payable-agings?legal_entity_reference=&book_reference=&fiscal_period_reference=` return the inverted credit-normal worksheet for the catalog `tax_payable` account (seeded 210100): credit lines age from `accounting_date` and debit tax-unwinds consume the oldest open credit first. `total_outstanding_amount` equals `GET /account-balances` net (`credit_amount` − `debit_amount`) for that payable. This slice does not add `party_reference`. `GET /period-close-packages` includes that same payable-aging document as `payable_aging`. `lookup_legal_entities` and `GET /legal-entities` list existing `legal_entity_record` rows for the bound tenant (`legal_entity_reference` from `legal_entity_code`, and `entity_name`); empty tenants return `legal_entities` []. `lookup_accounting_books` and `GET /accounting-books?legal_entity_reference=` list existing `accounting_book` rows for that tenant entity (`accounting_book_reference` / `book_reference` from `book_name`, `intended_book_role_code` from `book_role_code`, and `book_name`); empty entities return `accounting_books` []. `lookup_chart_accounts` and `GET /chart-accounts?legal_entity_reference=&book_reference=` return existing `chart_account` rows (`chart_account_code`, `account_name`, `normal_balance_code`, `account_class_code`). `lookup_financial_statement` and `GET /financial-statements?legal_entity_reference=&book_reference=&fiscal_period_reference=&statement_type_code=` project an income statement, balance sheet, statement of changes in equity, or statement of cash flows using `account_class_code` to split revenue/expense from asset/liability/equity. `statement_type_code=changes_in_equity` returns movement rows `opening_equity`, `period_net_income`, `other_equity_movements`, and `closing_equity` that roll opening equity plus operational net income plus other equity-class journals (excluding the AIS period-closing journal) to closing equity, which ties to the balance-sheet equity total for the same scope. `statement_type_code=cash_flow` returns IAS 7 indirect movement rows `period_net_income`, `operating_working_capital`, `cash_from_operations`, `cash_from_investing`, `cash_from_financing`, `net_cash_change`, `opening_cash`, and `closing_cash`. Cash is the current `cash_receipt` mapping. Working capital is the non-cash asset and liability class change, signed so an AR increase reduces operating cash. Financing reuses other equity movements. Investing stays 0 unless a non-cash non-equity asset acquisition already exists. Rows are credit-normal (cash increase on `credit_amount`). `closing_cash` equals opening plus net cash change and the balance-sheet cash total for the same scope. Optional `statement_scope_code` is `period` or `year_to_date`; omit or `period` keeps today's keys and returns that period's operational P&L, as-of sheet, period equity movement, or period cash flow. `year_to_date` sums same-year income-statement, equity-movement, and cash-flow activity through `fiscal_period_reference` and reuses the period balance sheet; the document then includes `statement_scope_code`. Optional `comparison_fiscal_period_reference` adds prior-period `comparison_statement_lines` and comparison totals on that same document using the same scope; omitting the comparison leaves today's keys unchanged. Income-statement lines exclude AIS period-closing journals so period earnings match pre-close activity. After hard-close the balance sheet includes 310100 and `net_income_amount` is 0; changes in equity and cash flow still report that pre-close result and do not count the closing journal as an other movement, working-capital change, or financing. `lookup_financial_statement_package` and `GET /financial-statement-packages?legal_entity_reference=&book_reference=&fiscal_period_reference=` return those four statement documents for the same scope as one close pack. Optional `statement_scope_code` and `comparison_fiscal_period_reference` keep the single-statement omit rules; the package includes `statement_scope_code` only for `year_to_date`. `GET /financial-statements` stays the single-statement read. `lookup_period_close_package` and `GET /period-close-packages?legal_entity_reference=&book_reference=&fiscal_period_reference=` compose that pack with the exact `GET /fiscal-periods` document, omit-basis `GET /trial-balances`, default `GET /receivable-agings`, default `GET /payable-agings`, and the latest `GET /period-closes` item when a hard-close snapshot exists (`period_close` is `null` for open and `soft_closed`). Optional scope and comparison query keys are forwarded only into the inner financial-statement package. The binder does not reimplement statement, trial-balance, or aging math. `GET /healthz` is an ops probe. The HTTP server binds `0.0.0.0:$PORT` and accepts only the purpose-limited `X-CWL-Tenant-Reference` header on accounting routes. POST routes match `parsed_path` so a query string does not 404; request bodies over 1 MiB are 413. Naive list-cursor timestamps without a UTC offset are 422. `PostgresPostingLedger.post_proposal` resolves `AccountingPolicy` from the foundation catalog (`account_role_mapping`, book by intended role, open fiscal period) in the same transaction as the post. Catalog `write_off_expense` maps to chart `510100` (`account_class_code=expense`) so a Billing #51 collection write-off (debit write-off expense / credit accounts receivable) posts through that same ingest, HTTP `POST /journal-proposals`, and `billing_pull` path; hard-close parks `510100` into `retained_earnings` 310100 like other P&L, and the write-off journal remains `journal_source_code=billing`, not `period_closing`. `PostgresPostingLedger` also applies those invariants to PostgreSQL 18 through `database/migrations/0001_accounting_foundation.sql` and `database/migrations/0002_chart_account_class.sql`: one transaction writes the proposal, journal, lines, receipt, and outbox event; replay returns the original receipt; reversal is append-only; `close_fiscal_period` sets `soft_closed` without a snapshot or, on `hard_closed`, posts the closing journal and writes a trial-balance snapshot in one commit; a non-open fiscal period writes zero ordinary-posting rows. The in-memory `PostingLedger.post(proposal, policy)` path remains the reference oracle.

## Deployment evolution

1. Reference core and contracts.
2. PostgreSQL proposal-intake and posting transaction.
3. Journal-proposal accept HTTP POST and operator hold queue.
4. Billing integration and source-to-posting reconciliation.
5. Revenue accounting and settlement accounting.
6. Cash, ISO 20022 adapters, multi-currency, reporting, and consolidation.

The modules may remain in one deployable service until throughput, data residency, or independent control ownership justifies separation. Service boundaries must not introduce direct cross-service SQL.
