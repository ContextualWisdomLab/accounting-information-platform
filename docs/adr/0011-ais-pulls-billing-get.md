# ADR 0011: AIS pulls Billing GET and does not flip proposal status

**Status:** Accepted

## Decision

AIS is a Billing GET consumer. `POST /billing-proposal-pulls` and `accept_billing_proposal_pull` trust `BILLING_BASE_URL` plus optional `BILLING_ALLOWED_ORIGINS` as the only allowed origins. A request-body `billing_base_url` must match that allowlist or fail closed; omit uses the env origin. Configured origins are normalized to `scheme://host[:port]`, must be HTTP(S), and are rejected when the host is loopback, link-local, or `localhost`; placing such an origin in `BILLING_ALLOWED_ORIGINS` does not override that safety rule. AIS never treats a request-body URL as authority for a new destination.

`pull_validated_journal_proposals` calls `GET {resolved origin}/v1/journal-proposals` with purpose-limited `X-CWL-Tenant-Reference` and the same `tenant_reference` query value, `proposal_status=validated`, inclusive `proposed_after`, query `cursor`, and `page_limit` (default 50, maximum 100). The list body keys are only `journal_proposals` and `next_cursor`. There is no body `items` field and no body `cursor` field. AIS fails closed if invented envelope keys appear. Each list item is the same published `accounting_journal_proposal` object as `GET /v1/journal-proposals/{proposal_id}` (no envelope). Order is `proposed_at` then `proposal_id`. AIS passes `next_cursor` back as query `cursor` and treats `{"journal_proposals":[],"next_cursor":null}` as the empty page. AIS drops any wire item whose `proposal_status` is not `validated`. `pull_journal_proposal` treats HTTP 404 as unknown or cross-tenant without retrying as another tenant.

`accept_pulled_proposals` is deliberately **page-progressive, not an all-pages database transaction**. Each validated proposal is posted through the ordinary AIS posting transaction before the next page is fetched. Therefore an initial Billing GET failure writes zero AIS rows, but a failure on a later page does not roll back receipts already committed from earlier pages. The operator retries the same pull boundary (same tenant and cursor/proposed-after policy); exact proposal idempotency replays previously committed receipts without duplicating journals, and the pull can continue from durable evidence. The response includes successful `posting_receipts` and per-item `rejected_proposals`; an item-level validation failure does not abort the page. A repeated or non-advancing `next_cursor` stops the pull at 422. A pull longer than 20 pages also stops at 422 so the HTTP request cannot hang. AIS does not claim atomic rollback across remote Billing pagination.

After ingest and post, AIS does not call Billing to mark a proposal `exported`, `posted`, or consumed. It does not invent a Billing `proposal_status`. `POST /billing-proposal-pulls` exposes the same command and always includes `posting_receipts` and `rejected_proposals` when the command reaches a normal completed response.

## Consequences

Cash and invoice proposals share Billing's `journal_proposal` store and enter AIS through one pull. Operators reconcile Billing `GET /v1/journal-proposals` against authoritative AIS posting receipts and rejected rows. If a later remote page fails, operators retry; previously posted proposals replay deterministically instead of being duplicated or silently rolled back. Semantic roles remain `accounts_receivable`, `usage_revenue`, and `cash_receipt`; AIS catalog mapping still selects 110100, 410100, and 110200. Billing remains the proposal-status authority. AIS remains the posting-receipt authority.
