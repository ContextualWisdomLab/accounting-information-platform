# ADR 0011: AIS pulls Billing GET and does not flip proposal status

**Status:** Accepted

## Decision

AIS is a Billing GET consumer. `POST /billing-proposal-pulls` and `accept_billing_proposal_pull` trust `BILLING_BASE_URL` plus optional `BILLING_ALLOWED_ORIGINS` as the only allowed origins. A request-body `billing_base_url` must match that allowlist or fail closed; omit uses the env origin. AIS does not fetch `file://`, link-local, or loopback unless that exact origin is allowlisted. Production configuration does not allowlist loopback. `pull_validated_journal_proposals` calls `GET {resolved origin}/v1/journal-proposals` with purpose-limited `X-CWL-Tenant-Reference` and the same `tenant_reference` query value, `proposal_status=validated`, inclusive `proposed_after`, query `cursor`, and `page_limit` (default 50, maximum 100). The list body keys are only `journal_proposals` and `next_cursor`. There is no body `items` field and no body `cursor` field. AIS fails closed if those invented keys appear. Each list item is the same published `accounting_journal_proposal` object as `GET /v1/journal-proposals/{proposal_id}` (no envelope). Order is `proposed_at` then `proposal_id`. AIS passes `next_cursor` back as query `cursor` and treats `{"journal_proposals":[],"next_cursor":null}` as the empty page. AIS drops any wire item whose `proposal_status` is not `validated`. `pull_journal_proposal` treats HTTP 404 as unknown or cross-tenant without retrying as another tenant. `accept_pulled_proposals` pages until `next_cursor` is empty and posts each validated item through `accept_journal_proposal`. Replay of the same tenant, Billing `idempotency_key`, and `source_payload_hash` returns the same `accounting_posting_receipt` and writes no second journal. A failed item fails closed for that item, does not abort the page, and is returned on `rejected_proposals` with `proposal_id`, `idempotency_key`, a stable `rejection_reason_code`, and the existing `AccountingValidationError` next-action sentence. AIS does not invent a Billing `proposal_status`. A repeated or non-advancing `next_cursor` stops the pull at 422. A pull longer than 20 pages also stops at 422 so the HTTP thread cannot hang. A failed Billing GET writes zero AIS rows. After ingest and post, AIS does not call Billing to mark a proposal `exported`, `posted`, or consumed. `POST /billing-proposal-pulls` exposes the same command and always includes `posting_receipts` and `rejected_proposals`.

## Consequences

Cash and invoice proposals share Billing's `journal_proposal` store and enter AIS through one pull. Operators can reconcile Billing `GET /v1/journal-proposals` against posted receipts and rejected rows. Semantic roles remain `accounts_receivable`, `usage_revenue`, and `cash_receipt`; AIS catalog mapping still selects 110100, 410100, and 110200. Billing remains the proposal-status authority. AIS remains the posting-receipt authority.
