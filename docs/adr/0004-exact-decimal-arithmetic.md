# ADR 0004: Exact decimal arithmetic

**Status:** Accepted

## Decision

Amounts use canonical decimal strings at interfaces, `decimal.Decimal` in the Python reference core, and PostgreSQL `numeric(38, 6)` in the initial schema. Binary floating point is prohibited for accounting arithmetic.

A debit or credit may have at most six digits after the decimal point. The published `positive_decimal` / `non_negative_decimal` patterns and `_parse_amount` use `^(0|[1-9][0-9]*)(\\.[0-9]{1,6})?$`. A longer value such as `0.0000010` is rejected; AIS does not coerce or round it to fit `numeric(38, 6)`. Integers and typical two-place Billing KRW amounts still pass. `positive_decimal` also excludes an all-zero string so the non-zero side of a line stays positive.

The published Billing proposal contract keeps amounts as strings. `ingest_journal_proposal` rejects JSON numbers, including integers and floats such as `25000.5`, before `str(value)` can satisfy the canonical-decimal regex. A missing amount key is a validation error, not a `KeyError`.

General Ledger double-entry validation is mathematical equality over the admitted canonical decimals and must not depend on the process-wide or caller-local `decimal` precision context. Journal proposal debit/credit totals therefore sum exact base-10 coefficients rather than using context-sensitive `Decimal` addition. The same exact sum is returned by the public `debit_total` and `credit_total` properties.

Construction-time validation is not the posting authority boundary. A frozen Python value object can still be altered through low-level deserialization or `object.__setattr__` before it reaches `PostingLedger.post()`. The posting command therefore recomputes the proposal's current exact debit and credit totals before idempotent replay lookup or line resolution and fails closed if the proposal no longer balances. A proposal that was balanced only at construction time is not sufficient evidence for posting.

Aggregate balance alone is also insufficient posting evidence. The posting command snapshots the current proposal lines into freshly validated `JournalLineProposal` values before idempotent replay lookup, then rechecks minimum line population, unique line numbers, per-line semantic role, canonical debit/credit amounts, exactly-one-positive-side semantics, and exact aggregate balance on that snapshot. A caller cannot preserve total debits and credits while mutating individual lines into two-sided, zero-sided, duplicate-number, or undersized populations and still obtain a posting or cached replay receipt.

Journal line identity has its own runtime domain. `JournalLineProposal.line_number` must be an exact built-in positive `int` before positivity, uniqueness, retention, or replay control uses it. Boolean values and `int` subclasses are rejected before Python or caller-defined integer ordering can participate. Because `PostingLedger.post()` rebuilds every current line before cache lookup, post-construction mutation of a previously valid line number is re-admitted through the same rule and cannot be hidden by an idempotent receipt.

Journal semantic role is executable posting identity rather than presentation text. `JournalLineProposal.account_role_code` must be an exact built-in `str` before lower-snake-case syntax validation. Non-strings and `str` subclasses are rejected before regular-expression behavior, chart-account mapping hashing, or cached replay can consume caller-owned runtime behavior. The existing posting-time line reconstruction reapplies this boundary to the current role value before replay lookup, so a post-construction role mutation cannot be hidden by a retained receipt.

The proposal envelope is part of the same posting evidence. After the line snapshot is admitted, `PostingLedger.post()` reconstructs a fresh `JournalProposal` from the current proposal identity, contract version, idempotency key, tenant/entity/book-role scope, currency, dates, source payload hash, source-event references, and validated line snapshot. Cache lookup, policy validation, journal identity construction, retained facts, and receipt caching use only that validated proposal snapshot. A cached receipt does not authorize replay of an envelope that no longer satisfies the repository's proposal admission contract.

Proposal contract version is executable envelope identity. `proposal_contract_version` must be an exact built-in positive `int`; booleans and `int` subclasses are rejected before positivity comparison, cache lookup, or retained posting evidence. The posting-time envelope reconstruction reuses this rule, so a previously valid proposal whose contract version is mutated cannot obtain a cached receipt without current admission.

The proposal idempotency key is executable posting command identity. `JournalProposal.idempotency_key` must be an exact built-in non-empty `str` before cached replay identity is read or written. Truthy non-strings and `str` subclasses are rejected; AIS does not coerce command identity or allow caller-defined hashing or equality behavior to participate in replay control. Reconstructing the current proposal envelope at `PostingLedger.post()` reuses this admission before cache lookup, so post-construction mutation cannot hide an invalid current command identity behind a retained receipt.

Proposal dates are executable accounting evidence, not annotation-only values. `transaction_date` and `accounting_date` must be exact built-in `datetime.date` values; strings, `datetime.datetime`, and date subclasses are rejected before policy period comparison, retained journal construction, or cached replay. Rebuilding the envelope at `PostingLedger.post()` therefore also revalidates the current date runtime domain after any post-construction mutation.

The proposal source payload hash is executable provenance and replay evidence. `source_payload_hash` must be an exact built-in `str` matching the canonical `sha256:` plus 64 lowercase hexadecimal digits before it can be retained or compared with cached command evidence. Non-strings and `str` subclasses are rejected before regular-expression admission or equality/inequality can delegate to caller-defined behavior. The posting-time envelope reconstruction applies the same admission before `_cached_idempotency_receipt()`.

Opaque CWL references are executable accounting identity/provenance, not annotation-only strings. `_require_reference()` therefore admits only exact built-in `str` values that satisfy the canonical `urn:cwl:` syntax. Non-strings and `str` subclasses fail before regex admission, dictionary hashing, equality, filtering, command hashing, or retained provenance can delegate to caller-defined behavior. This one shared runtime boundary covers proposal tenant/entity scope, source-event references, policy scope, reversal targets, and trial-balance selectors without duplicating field-specific coercion.

Construction-time policy validation is likewise insufficient at posting and reversal command boundaries. `AccountingPolicy` reference fields can be mutated after construction through low-level object mutation, so `PostingLedger.post()` revalidates current tenant, legal-entity, and accounting-book references before idempotent replay lookup or retained journal/receipt construction. `PostingLedger.reverse()` revalidates the same three references before reversal command hashing or tenant-scoped cache access. A cached posting or reversal receipt therefore cannot authorize caller-owned reference behavior that was introduced after policy construction.

Trial-balance arithmetic is the same accounting-control domain. Per-account debit and credit accumulation and `AccountBalance.net_balance` must preserve every admitted base-10 unit independently of the active `decimal` precision context. The reference core therefore reuses `_exact_decimal_sum()` for both trial-balance sides and for debit-minus-credit rather than relying on ambient-context `Decimal` addition or subtraction. This is exact mathematical aggregation, not a rounding or presentation policy.

The trial-balance cutoff is executable read-control evidence. `through_date` must be an exact built-in `datetime.date` before any posted-journal date comparison. Strings, `datetime.datetime`, and date subclasses are rejected through the same repository-owned calendar-date admission so caller-defined comparison behavior cannot decide which journals enter an accounting balance read.

The trial-balance tenant, legal-entity, and accounting-book selectors are also read-control evidence. Each selector must be an exact built-in `str` satisfying the canonical opaque CWL URN reference contract before journal filtering. A malformed or caller-owned selector must fail closed rather than be interpreted as a legitimate but empty ledger scope, because an empty balance caused by invalid identity is not equivalent to an empty balance in a valid tenant/entity/book scope.

## Consequences

Rounding, scale, foreign exchange, and reporting currency treatment require explicit versioned policy rather than implicit language or database defaults. Billing cannot smuggle a binary float through HTTP accept into the ledger.

A journal, trial balance, or account net balance cannot become apparently balanced, unbalanced, lose a low-order unit, select its journal population through caller-defined date behavior, silently collapse an invalid read identity into an empty scope, or let caller-defined integer/string subtypes participate in retained line identity, semantic role selection, proposal-contract, tenant, source-provenance, policy, reversal-target, or read-scope identity solely because an embedding caller changed Python runtime state or supplied malformed control values. Posting or reversal cannot rely on stale constructor-time policy references, and cached receipts cannot bypass current policy-reference admission. Posting cannot rely on stale constructor-time aggregate balance, stale per-line semantics, a stale proposal envelope, semantic account roles outside the exact built-in lower-snake-case string domain, command identity outside the exact built-in non-empty string domain, source payload provenance outside the exact built-in canonical SHA-256 string domain, opaque accounting references outside the exact built-in canonical CWL URN domain, line identity outside the exact built-in positive-integer domain, contract version outside the exact built-in positive-integer domain, or date values outside the exact calendar-date runtime domain when executable state has changed before the posting boundary. Future monetary aggregate paths must either reuse an exact context-independent arithmetic primitive or document an explicit versioned rounding/scale policy before arithmetic is used as accounting authority. These Python runtime-domain rules are repository invariants, not claims that IFRS/IASB prescribes Python types or CWL identifier syntax.
