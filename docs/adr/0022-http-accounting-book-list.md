# ADR 0022: HTTP accounting-book list

**Status:** Accepted historical catalog contract; effective-time durable-reference uniqueness amendment Proposed in #58

## Historical decision

AIS exposes `lookup_accounting_books` and `GET /accounting-books?legal_entity_reference=` on the same stdlib HTTP surface as chart-account and mapping catalog reads. The only request identity header is purpose-limited `X-CWL-Tenant-Reference`. The read returns existing `accounting_core.accounting_book` rows for that tenant legal entity. `book_name` is the durable book identity already returned as `accounting_book_reference` and `book_reference` on trial-balance, chart-account, and financial-statement documents. `book_role_code` is returned as `intended_book_role_code`, the name already used on proposals and policy. `book_name` is also returned because that column exists. The list does not invent a book-code column, a list table, or paging; the catalog is small and ordered by `book_name`. An empty entity returns `accounting_books` [] rather than 404. A missing legal entity fails closed. `POST /accounting-books` is 405. A tenant-header mismatch is rejected before the read and writes zero rows.

Controllers can discover `book_reference` without SQL before calling `GET /trial-balances`, `GET /chart-accounts`, `GET /account-role-mappings`, or `GET /financial-statements`. Book authority remains the existing `accounting_book` population.

## Review finding

Protected migration 0001 does not enforce the identity implied by that public contract. `accounting_core.accounting_book` is unique on `(tenant_account_id, legal_entity_id, book_role_code, valid_from)` and UUID-based keys, but not on non-overlapping `(tenant_account_id, legal_entity_id, book_name)` effective-time identity. Two Accounting Book Entities can therefore expose the same durable `book_reference` while their validity intervals overlap and while they carry different `accounting_book_id` and role identity.

A consumer that resolves `book_reference` with `.fetchone()`, implicit row order, a default `book_role_code`, or current account mappings can consequently bind an arbitrary Accounting Book Entity. PR #57 exposed the immediate General Ledger risk while preparing book-scoped ledger reads; Issue #58 owns the underlying catalog invariant.

The database gap is not limited to inserts. `valid_from` / `valid_to` are effective-time state, so an initially lawful pair of adjacent or disjoint rows can become ambiguous through a later validity update unless the same database-owned invariant is enforced on mutation. Both boundary columns are material: moving a successor `valid_from` backward or extending a predecessor `valid_to` forward can create the same overlapping durable identity. An insert-only trigger, a trigger bound to only one boundary column, or application preflight is therefore insufficient even before concurrency is considered.

Protected resolver behavior also collapses effective time to `valid_to IS NULL` in multiple accounting paths. That shortcut can resolve a future-scheduled open-ended book before `valid_from`, while rejecting a finite row that is effective now but has a scheduled `valid_to`. Temporal non-overlap in the database therefore does not make resolver semantics correct by itself: a durable reference must be evaluated at an explicit effective instant using the same half-open interval convention.

`bank_account_assignment` adds a separate temporal referential-integrity requirement. Migration 0011 gives that relationship composite foreign keys to its tenant, legal entity, Accounting Book and chart account, but those foreign keys prove only relational identity. They do not prove that the assignment interval remains inside the referenced Accounting Book interval. A parent `accounting_book.valid_to` update can therefore strand a previously lawful assignment so that the relationship remains effective after its book has ceased to exist. Admission-time lookup alone cannot close this path because the later parent mutation bypasses that check.

The same assignment admission path also resolves `chart_account` with `valid_to IS NULL` only. Because `accept_bank_account_assignment()` already owns assignment `valid_from`, a future-scheduled open-ended chart account can be selected before its own `valid_from` even when the referenced Accounting Book is already effective. This is a scoped Bank Reconciliation relationship defect: the assignment must not become effective before the exact referenced chart-account Entity does. It does not establish a blanket temporal-containment policy for every effective-dated relationship.

This is an AIS accounting-master-data identity defect. IFRS does not prescribe the PostgreSQL key, range type, index, constraint, or resolver API used to repair it. The database and resolver mechanisms remain repository-owned controls supporting deterministic accounting-book identity, tenant/legal-entity scope, effective-time history, and downstream financial-control traceability.

## Proposed amendment

Within one tenant and legal entity, an externally durable `book_name` / `book_reference` must identify at most one Accounting Book Entity at any effective instant. Historical effective-dated rows may retain the same reference only when their validity intervals do not overlap. Preserving non-overlapping history is required so posted facts and prior evidence are not rewritten merely because the current book catalog changes.

For this amendment an Accounting Book validity interval is half-open: `[valid_from, valid_to)`, with `valid_to IS NULL` extending to positive infinity. `valid_to` is therefore the first instant at which that Entity is no longer effective. Two same-reference intervals that only touch at one boundary are lawful; treating the shared endpoint as overlap would reject a lossless effective-dated handoff without improving identity safety.

The canonical repair should therefore:

- enforce non-overlapping effective-time identity for `(tenant_account_id, legal_entity_id, book_name)` in PostgreSQL for both INSERT and effective-time UPDATE, across open-ended and finite validity intervals and regardless of whether `valid_from` or `valid_to` is mutated;
- retain expired or superseded historical rows with the same `book_name` only when their effective intervals do not overlap, including lawful `[a, b)` / `[b, c)` adjacency;
- make public resolvers evaluate the durable reference at an explicit effective instant with `valid_from <= effective_at` and `(valid_to IS NULL OR valid_to > effective_at)`, then fail closed on zero or multiple matches rather than selecting a row by ordering or role inference;
- use an accounting-effective instant supplied by the owning use case for period/journal/history operations; only genuinely current catalog operations may derive the effective instant from the database clock, and system/recorded time must not be substituted for historical accounting effective time;
- keep each `bank_account_assignment` interval temporally contained in its referenced Accounting Book interval. An assignment valid through `[a, b)` may not reference a book outside `[a, b)`, and later mutation of either the parent book or assignment boundaries must fail closed if it would break that containment;
- require the chart account selected for a `bank_account_assignment` to be effective at the assignment's own `valid_from`; a current/open-ended chart-account shortcut must not admit a future-scheduled account early;
- preserve `accounting_book_id` as the immutable relational Entity key used by journals, chart accounts, close evidence, reconciliation and reporting sources;
- preserve tenant RLS/composite-FK boundaries, reporting-currency facts and effective/system-time evidence;
- reject upgrade if existing overlapping book references or `bank_account_assignment` rows outside their referenced Accounting Book interval cannot be reconciled without an explicit accounting-master-data decision; migration code must not silently rename, merge, truncate, or delete books or assignments.

A database-owned temporal non-overlap constraint or equivalent invariant is preferred over application-only validation because concurrent catalog writes must not create ambiguous authority and later validity updates must not bypass the same rule. The same reasoning applies specifically to `bank_account_assignment` containment: validating only when an assignment is created does not protect the invariant when the parent book is later shortened. A partial unique index limited to `valid_to IS NULL` is insufficient by itself: it prevents duplicate open-ended rows but still permits finite rows whose validity overlaps an open-ended or another finite row. Resolver cardinality checks remain defense in depth and provide a stable fail-closed error if legacy/corrupt state is encountered.

## Alternatives rejected

Making `book_role_code` part of the public identity is rejected because ADR 0022 already exposes `book_name` as the durable reference and callers should not have to infer an accounting role to disambiguate one identifier. Selecting the first match is rejected because result identity would depend on query order. A current-row-only uniqueness rule is rejected because it does not protect effective-time reads from overlapping historical/future intervals. Treating `valid_to IS NULL` as synonymous with "effective now" is rejected because it admits future-scheduled open-ended rows and excludes currently effective finite rows. An insert-only validation path is rejected because a lawful historical interval can later be edited into overlap. A one-sided update trigger is rejected because changing either `valid_from` or `valid_to` can create overlap. Application-only assignment admission validation is rejected as the sole `bank_account_assignment` control because a later direct or owner-path parent-book validity mutation can make an already-recorded assignment invalid without re-running admission. Resolving the assignment's chart account with `valid_to IS NULL` alone is rejected because it substitutes current/open-ended state for the assignment's explicit effective instant. Making `book_name` globally unique for all history is rejected because it would prevent lawful non-overlapping effective-dated history. Closed-interval semantics are rejected because they would make a row ending at `t` conflict with its successor beginning at `t`, despite no instant having two effective Entities under the repository's established `valid_from <= t` / `valid_to > t` convention. Rewriting posted journals or retained evidence to a newly chosen book is rejected because posted accounting facts are immutable.

## Implementation and evidence boundary

Positive cases retain non-overlapping expired history and require exact-boundary adjacency to remain lawful. Resolver REDs separately require 0/1/>1 cardinality handling so impossible or corrupt multiplicity cannot collapse to `.fetchone()` ordering.
