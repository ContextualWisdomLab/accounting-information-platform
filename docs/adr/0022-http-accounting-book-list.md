# ADR 0022: HTTP accounting-book list

**Status:** Accepted historical catalog contract; effective-time durable-reference and Bank Reconciliation evidence amendment Proposed in #59

## Historical decision

AIS exposes `lookup_accounting_books` and `GET /accounting-books?legal_entity_reference=` on the same stdlib HTTP surface as chart-account and mapping catalog reads. The only request identity header is purpose-limited `X-CWL-Tenant-Reference`. The read returns existing `accounting_core.accounting_book` rows for that tenant legal entity. `book_name` is the durable book identity already returned as `accounting_book_reference` and `book_reference` on trial-balance, chart-account, and financial-statement documents. `book_role_code` is returned as `intended_book_role_code`, the name already used on proposals and policy. `book_name` is also returned because that column exists. The list does not invent a book-code column, a list table, or paging; the catalog is small and ordered by `book_name`. An empty entity returns `accounting_books` [] rather than 404. A missing legal entity fails closed. `POST /accounting-books` is 405. A tenant-header mismatch is rejected before the read and writes zero rows.

Controllers can discover `book_reference` without SQL before calling `GET /trial-balances`, `GET /chart-accounts`, `GET /account-role-mappings`, or `GET /financial-statements`. Book authority remains the existing `accounting_book` population.

## Review finding

Protected migration 0001 does not enforce the identity implied by the public contract. `accounting_core.accounting_book` is unique on `(tenant_account_id, legal_entity_id, book_role_code, valid_from)` and UUID-based keys, but not on non-overlapping `(tenant_account_id, legal_entity_id, book_name)` effective-time identity. Two Accounting Book Entities can therefore expose the same durable `book_reference` while their validity intervals overlap and while they carry different `accounting_book_id` and role identity. A consumer that resolves `book_reference` with `.fetchone()`, implicit row order, a default `book_role_code`, or current account mappings can bind an arbitrary Entity.

The gap is not limited to inserts. Moving a successor `valid_from` backward or extending a predecessor `valid_to` forward can turn lawful adjacent history into overlapping durable identity. Protected resolver paths also substitute `valid_to IS NULL` for effective-time selection, which can select a future-scheduled open-ended Book before `valid_from` and can exclude a finite Book that is effective at the requested accounting instant.

`bank_account_assignment` adds a scoped Bank Reconciliation temporal-integrity problem. Migration 0011 composite foreign keys prove relational scope but do not prove that the assignment interval remains inside its exact Accounting Book or chart-account Entity interval. Admission currently resolves Book and chart account with current/open-ended shortcuts even though the command owns `valid_from`. An initially lawful relationship can later become invalid when either parent or child validity boundary moves.

Migration 0012 separately says that a second active binding for one tenant, bank account, and Accounting Book is a data defect, but its partial unique index defines active only as `valid_to IS NULL`. It therefore permits overlapping finite assignments and finite assignments overlapping an open-ended row. It also cannot serialize two concurrent overlapping writers that both pass an application-side preflight.

Migration 0012 introduces `assignment_idempotency_key` as replay identity and describes `assignment_command_hash` as immutable SHA-256 command evidence. The protected schema has three independent defects here. First, the hash CHECK is only `assignment_command_hash LIKE 'sha256:%'`; it accepts short, overlong, non-hex, and uppercase representations that are not the canonical digest emitted by `_assignment_command_hash()`. Canonical retained evidence is exactly `sha256:<64 lowercase hexadecimal characters>`. Second, syntax alone does not prove that a well-formed digest belongs to the row being admitted: direct PostgreSQL INSERT can reuse a canonical hash from a different bank-account assignment while changing the bank-account identity, leaving formally valid but false retained command evidence. Third, even a canonical accepted key/hash can later be replaced because neither column is update-immutable.

The same row carries PostgreSQL-owned `recorded_at`, database-generated `bank_account_assignment_id`, accepted `valid_from`, and the relationship identity represented by `bank_account_record_id`, `legal_entity_id`, `accounting_book_id`, and `chart_account_id`. The protected schema permits those facts to be rewritten in place, permits mutually consistent multi-column FK rebinds, and permits physical DELETE when no downstream FK happens to block it. Exact replay can consequently return a different row or relationship while retaining the original replay key/hash.

Retaining the assignment row and its foreign keys is still insufficient if a parent Entity can rewrite the public reference that the command hash committed. `_assignment_command_hash()` includes `bank_account_reference`, while exact replay joins `bank_account_assignment.bank_account_record_id` back to the current `bank_account_record.bank_account_reference`. Protected migration 0011 has no UPDATE guard on `bank_account_record`. A tenant-authorized writer can therefore rename a linked bank-account reference to a fresh unique value without changing the assignment row, its idempotency key, or its command hash; exact replay would then describe a different public identity than the accepted command. This is a parent-identity evidence drift, not an assignment-FK rebind.

The bank-account parent has its own retained command-evidence defect even when its public reference does not change. `accept_bank_account_record()` treats `(bank_account_reference, account_currency_code, account_identifier_hash)` as one replay contract: reusing the reference with different currency or identifier evidence raises an idempotency conflict. Migration 0011 nevertheless allows a tenant-authorized writer to replace `account_currency_code` with another valid ISO currency or `account_identifier_hash` with another syntactically canonical SHA-256 value in place. The accepted registration also exposes a database-generated `bank_account_record_id` and PostgreSQL-owned `recorded_at`, yet an otherwise unreferenced registration can currently have either value rewritten or the row physically deleted. Those mutations can erase or replace the Entity and its system-time provenance even though the supported command path treats the registration as durable evidence.

The immutable bank-statement artifact registry has a symmetric admission-provenance defect. `accept_bank_statement_evidence()` omits `bank_statement_artifact_id` and `recorded_at`, relying on migration 0011 `DEFAULT uuidv7()` and `DEFAULT clock_timestamp()`, and the same migration installs UPDATE/DELETE immutability guards after admission. PostgreSQL defaults only apply when a column is omitted. A tenant-authorized direct INSERT can therefore supply a caller-chosen artifact UUID or historical timestamp and have that caller claim become immutable evidence unless admission either rejects it or replaces it with a server-owned value.

The immutable `bank_statement_record` has the same admission-provenance defect. The supported ingest path omits `bank_statement_record_id` and `recorded_at`, delegating both to PostgreSQL, but migration 0011 accepts explicit values for either column before its UPDATE/DELETE immutability guard applies. A tenant-authorized direct INSERT can therefore freeze a caller-chosen statement-record UUID or historical system timestamp as if it were database-owned provenance.

Statement-record source provenance is also relational, not merely syntactic. The supported ingest path writes the same parsed `statement.source_artifact_hash` into `bank_statement_artifact.source_artifact_hash` and `bank_statement_record.source_artifact_hash`, but migration 0011's FK binds only `(tenant_account_id, bank_statement_artifact_id)`. Direct SQL can therefore reference immutable artifact A while retaining a different canonical SHA-256 B in the immutable statement record. The UPDATE/DELETE guard then preserves a detached source claim unless PostgreSQL binds the duplicate digest to the exact referenced artifact or admission is otherwise database-owned.

The immutable `bank_statement_entry` and `bank_statement_entry_detail` rows continue that provenance chain. The supported ingest path omits each row's UUID and `recorded_at`, relying on PostgreSQL defaults before UPDATE/DELETE immutability begins. Migration 0011 nevertheless accepts explicit values for those columns. A tenant-authorized direct INSERT can therefore freeze caller-selected entry/detail identities or historical system timestamps inside evidence that later reconciliation traces treat as immutable source facts.

Row immutability also does not close the retained child population. `accept_bank_statement_evidence()` parses the complete statement, computes `normalized_payload_hash` and each `source_entry_hash`, then inserts the statement, entries, and details together in one supported transaction. Migration 0011 prevents UPDATE/DELETE of retained statement, entry, and detail rows but still permits a later INSERT of a new `bank_statement_entry` under an already accepted statement or a new `bank_statement_entry_detail` under an already accepted entry. Those late children change the relational evidence population without changing the immutable parent `normalized_payload_hash` or `source_entry_hash`, so the database can contain two contradictory representations of the same accepted source evidence.

The hash chain also omits one field that the parser and PostgreSQL explicitly retain as transaction-detail evidence. `_normalize_detail()` reads `TxDtls/Refs/AcctSvcrRef` into `NormalizedEntryDetail.account_servicer_reference`, and the ingest path persists that value in `bank_statement_entry_detail.account_servicer_reference`, but `source_detail_hash` excludes it. `_entry_payload()` likewise excludes detail-level `account_servicer_reference`, so the omission propagates into the containing `source_entry_hash` and statement `normalized_payload_hash`. Two source-real statements that differ only in a retained detail servicer reference can therefore have distinct raw artifact hashes while sharing all three normalized evidence hashes, allowing same-statement-identity replay to treat changed retained reference evidence as identical.

`valid_to` is different because it is the relationship-retirement transition. A finite end supplied by the original command is lawful original command evidence. A post-acceptance close or end-date amendment, however, is a new accounting-effective transition and cannot be represented by an unaudited bare `UPDATE ... SET valid_to = ...`. Protected migration 0011/0012 currently has no close idempotency key, close-command hash, actor/approval evidence, or database-owned retirement entrypoint.

These are AIS accounting-master-data and Evidence-Audit defects. IFRS does not prescribe the PostgreSQL range type, key, trigger, exclusion constraint, resolver API, digest-binding mechanism, retirement command, server-owned provenance mechanism, population-closure mechanism, or canonical detail-evidence fields used to repair them. Repository-owned controls must provide deterministic identity, effective-time history, retained command/source evidence, and downstream financial-control traceability.

## Proposed amendment

Within one tenant and legal entity, an externally durable `book_name` / `book_reference` identifies at most one Accounting Book Entity at any effective instant. Historical rows may retain the same reference only when their validity intervals do not overlap. Validity is half-open `[valid_from, valid_to)`, with `valid_to IS NULL` extending to positive infinity; exact adjacency such as `[a,b)` / `[b,c)` is lawful.

The canonical repair must:

- enforce PostgreSQL-owned non-overlap for `(tenant_account_id, legal_entity_id, book_name)` on INSERT and on either effective-time boundary UPDATE, including concurrent writers;
- retain non-overlapping historical rows rather than rewriting posted-fact ancestry;
- resolve durable Book references at an explicit `effective_at` using `valid_from <= effective_at` and `(valid_to IS NULL OR valid_to > effective_at)`, failing closed on zero or multiple matches;
- use the owning accounting-effective fact for authoritative operations: `journal_date` for adjusting journals and assignment `valid_from` for bank-account assignment, rather than silently substituting database/system time;
- keep each `bank_account_assignment [a,b)` inside the exact referenced Accounting Book and chart-account Entity intervals from initial INSERT onward, and reject later parent/child boundary mutations that break containment;
- resolve the assignment chart account at assignment `valid_from`, including finite historical Entities and excluding future-scheduled Entities that have not begun;
- enforce non-overlapping effective-time assignment identity for `(tenant_account_id, bank_account_record_id, accounting_book_id)` on INSERT, both assignment-boundary UPDATE directions, and concurrent writes; finite/finite and open-ended/finite overlap fail closed while exact adjacency remains lawful;
- validate `assignment_command_hash` at initial PostgreSQL admission as exactly `sha256:<64 lowercase hexadecimal characters>`. Short, overlong, non-hex, uppercase, or otherwise noncanonical prefixed strings must fail closed before they become retained evidence;
- bind the admitted `assignment_command_hash` to the exact accepted assignment command, not merely its textual SHA-256 shape. A syntactically canonical digest copied from another assignment must fail closed when the bank/legal-entity/Book/chart/validity command evidence differs. The production mechanism may derive the digest inside a database-owned command entrypoint or retain enough immutable canonical command evidence to verify it, but a caller-supplied well-formed digest alone is not proof;
- preserve accepted `assignment_idempotency_key` and canonical, command-bound `assignment_command_hash` as immutable command evidence after INSERT;
- preserve database-generated `bank_account_assignment_id`, accepted `valid_from`, PostgreSQL-owned `recorded_at`, and accepted relationship identity (`bank_account_record_id`, `legal_entity_id`, `accounting_book_id`, `chart_account_id`) after INSERT;
- preserve any durable parent reference serialized into retained assignment command evidence for the exact referenced parent Entity. In particular, once an accepted assignment binds `bank_account_record_id`, its `bank_account_record.bank_account_reference` identity may not be renamed in place while the assignment retains the original command hash; a replacement public identity requires an explicit successor/master-data transition rather than retroactive relabeling;
- preserve the accepted `bank_account_record` registration as retained master-data evidence: its database-generated `bank_account_record_id`, durable `bank_account_reference`, accepted `account_currency_code` and `account_identifier_hash`, and PostgreSQL-owned `recorded_at` cannot be rewritten in place, and the accepted row cannot be physically deleted merely because no downstream FK currently references it. A genuine bank-account master-data change requires an explicit successor/transition contract rather than retroactively replacing or erasing the accepted registration;
- make bank-account registration identity and system time server-owned at initial admission as well as immutable afterward: direct SQL must reject caller-specified `bank_account_record_id` / `recorded_at` or replace those values before persistence rather than retaining caller claims under server-owned provenance semantics;
- make immutable `bank_statement_artifact` identity and system time server-owned at initial admission: where the supported ingest path delegates `bank_statement_artifact_id` and `recorded_at` to PostgreSQL, direct SQL must reject explicit caller values or replace them before the row becomes immutable;
- make immutable `bank_statement_record` identity and system time server-owned at initial admission: where the supported ingest path delegates `bank_statement_record_id` and `recorded_at` to PostgreSQL, direct SQL must reject explicit caller values or replace them before the row becomes immutable;
- make immutable `bank_statement_entry` identity and system time server-owned at initial admission: where the supported ingest path delegates `bank_statement_entry_id` and `recorded_at` to PostgreSQL, direct SQL must reject explicit caller values or replace them before the row becomes immutable;
- make immutable `bank_statement_entry_detail` identity and system time server-owned at initial admission under the same rule for `bank_statement_entry_detail_id` and `recorded_at`;
- bind `bank_statement_record.source_artifact_hash` to the exact `source_artifact_hash` retained by its referenced `bank_statement_artifact`; a syntactically canonical but different digest must fail closed rather than become immutable detached provenance;
- close the accepted statement-entry population: after `normalized_payload_hash` and the initial child set are retained, a direct SQL writer cannot append another `bank_statement_entry` beneath that statement unless a future explicit evidence-supersession protocol creates a new retained statement identity rather than mutating the accepted population;
- close the accepted entry-detail population under the same rule: once `source_entry_hash` and its initial details are retained, a later direct INSERT cannot add another `bank_statement_entry_detail` beneath that entry and thereby detach the relational population from the retained entry hash;
- include every retained transaction-detail field that is material to evidence identity in the canonical digest chain. In particular, changing `TxDtls/Refs/AcctSvcrRef` / `NormalizedEntryDetail.account_servicer_reference` must change `source_detail_hash`, the containing `source_entry_hash`, and `normalized_payload_hash`, so same-statement-identity replay fails closed rather than aliasing distinct retained reference evidence;
- reject FK-consistent multi-column rebinds as well as single-column rewrites. A changed binding is represented by an evidenced close of the prior assignment plus a successor command with new replay/hash evidence;
- reject physical DELETE of an accepted assignment; retained relationship history ends through a valid retirement transition rather than erasure;
- require every post-acceptance `valid_to` change to use an explicit idempotent retirement/amendment command that retains its own command evidence and authorization/audit facts. A finite `valid_to` supplied by the original assignment command remains lawful original evidence;
- preserve `accounting_book_id` as the immutable relational Entity key used by journals, chart accounts, close evidence, reconciliation, and reporting;
- preserve tenant RLS/composite-FK boundaries, reporting-currency facts, and the distinction between effective time and system time;
- fail upgrade/preflight on overlapping durable Book identity, overlapping same-bank/same-Book assignment identity, assignment intervals outside exact parents, malformed/noncanonical retained assignment hashes, syntactically valid hashes that cannot be proven to bind the retained command evidence, parent-reference drift that detaches replay output from retained command evidence, bank-account registration identity/system-time/evidence drift or erasure, bank-statement artifact provenance that cannot be shown to be server-owned, statement-record identity/system-time provenance that cannot be shown to be server-owned, statement-entry or entry-detail identity/system-time provenance that cannot be shown to be server-owned, statement records whose retained source digest cannot be proven to equal the referenced immutable artifact digest, accepted statement/entry child populations that cannot be proven to match their retained normalized/source hashes, normalized bank-statement digest chains that omit retained material detail evidence such as `account_servicer_reference`, or other retained evidence that cannot be trusted without an accounting-master-data decision. Migration code must not silently rename, merge, truncate, normalize, rehash, rebind, delete, append, or rewrite those facts.

A database-owned temporal non-overlap mechanism is preferred to application-only validation because concurrent writes and later boundary mutation must preserve the same invariant. PostgreSQL 18 temporal `WITHOUT OVERLAPS` is a candidate only if the canonical schema deliberately introduces a compatible range/multirange representation; the current separate `valid_from` / nullable `valid_to` columns do not satisfy that syntax by assertion. Assignment containment, effective uniqueness, hash syntax, command-to-hash binding, evidence immutability, system-time retention, relationship retention, parent-reference retention, bank-account command-evidence retention, bank-statement artifact/record/entry/detail admission provenance, statement-record/artifact source binding, immutable child-population closure, canonical detail-evidence hashing, and evidenced retirement may require distinct database mechanisms. The implementation must preserve semantics rather than force all controls into one construct.

## Alternatives rejected

Making `book_role_code` part of public Book identity is rejected because ADR 0022 already exposes `book_name` as the durable reference. Selecting the first matching row is rejected because identity would depend on query order. Current-row-only uniqueness and `valid_to IS NULL` resolver semantics are rejected because they do not represent effective time. Insert-only or one-sided mutation validation is rejected because either boundary can later create overlap or break containment. Application-only preflight is rejected as the sole database invariant because concurrent writers can both observe no committed conflict.

Migration 0012's prefix-only `LIKE 'sha256:%'` is rejected as SHA-256 validation: it proves neither the 64-character digest length nor lowercase hexadecimal alphabet. Format validation alone is also rejected as retained command evidence: a perfectly shaped digest can be copied from a different assignment and still lie about the accepted command. Unique/format constraints are likewise insufficient evidence immutability because a previously accepted row can be rewritten to fresh values that continue to satisfy them.

Protecting only replay key/hash while allowing assignment-id, accepted-start, relationship-FK, `recorded_at`, or row-deletion mutation is rejected because exact replay can return a different accepted fact or lose its system-time provenance. Protecting only the assignment row while allowing a hashed durable parent reference such as `bank_account_reference` to be renamed in place is rejected for the same reason: replay would retain the old command digest while returning a newly relabeled parent identity. Treating `bank_account_record` as freely mutable because replacement currency/hash values remain schema-valid, because its UUID/`recorded_at` are not themselves replay inputs, or because an unreferenced row has no downstream FK is rejected: the supported registration path exposes one durable master-data Entity whose identity, accepted evidence, system time and existence must not be retroactively replaced or erased. Treating `DEFAULT uuidv7()` or `DEFAULT clock_timestamp()` as proof of server-owned provenance is also rejected for bank-account registration and immutable statement artifact/record/entry/detail rows because explicit INSERT values bypass PostgreSQL defaults. Treating the statement/artifact FK plus two syntactically valid source hashes as provenance is rejected because that FK does not assert digest equality. Treating UPDATE/DELETE immutability on parent rows as complete source-evidence immutability is rejected because late child INSERTs can still change the accepted statement or entry population without changing the retained parent digest. Treating a retained detail column as immaterial merely because it was accidentally omitted from the digest serializer is rejected: if `account_servicer_reference` is persisted as immutable source evidence, its change cannot preserve the canonical detail/entry/statement hashes. Freezing `valid_to` completely is rejected because legitimate retirement must remain possible; unrestricted post-acceptance `valid_to` UPDATE is rejected because it changes accounting-effective history without a replayable transition command.

Global lifetime uniqueness of `book_name` and closed-interval semantics are rejected because they would destroy lawful effective-dated history and make an ending row conflict with a successor beginning at the same instant. Rewriting posted journals or retained evidence to a newly chosen Book is rejected because posted accounting facts are immutable.
