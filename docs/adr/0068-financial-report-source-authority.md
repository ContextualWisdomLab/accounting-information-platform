# ADR 0068: Bind financial-report source authority to AIS persistence

- Status: Proposed
- Date: 2026-09-04
- Owners: Accounting Information Platform
- Related: ADR 0001, ADR 0006, ADR 0021, ADR 0037, ADR 0049, ADR 0050, ADR 0067, Issue #51

## Context

ADR 0067 introduced a deterministic financial-report/XBRL proposal format but deliberately classified caller-supplied statement packages as `proposed`, `unverified`, and non-authoritative. A content hash can prove that bytes did not change; it cannot prove that the amounts, company, book, fiscal period, reporting currency, period state, or observation cutoff originated from the Accounting Information Platform.

The next commercial gap is therefore not another renderer. The platform needs a database-owned source registry that can prove which retained AIS snapshot population a later report artifact consumed. That registry must remain narrower than validation, approval, publication, filing, or regulator acceptance so those later responsibilities cannot be smuggled into a persistence identifier.

A concurrent reconciliation stack owns migrations 0015 through 0019. This change reserves migration 0020 for the financial-report source registry without copying or superseding reconciliation behavior. When the stacks are integrated, 0015–0019 remain the prerequisite sequence and 0020 follows them.

## Decision

Create two normalized records under `accounting_reporting`.

`financial_report_run` records one immutable accounting/reporting scope:

- tenant account;
- legal entity;
- accounting book;
- current fiscal period and optional comparison period;
- reporting currency derived from the referenced accounting book;
- current period status derived from the referenced fiscal period;
- database observation cutoff generated by PostgreSQL at run creation;
- caller purpose label retained as request context, not as proof of authority;
- a deliberately narrow lifecycle of `collecting_sources` or `superseded`.

`financial_report_source` records the retained evidence population used by that run:

- current or comparison period role;
- an existing `trial_balance_snapshot` foreign key;
- a fixed `financial_statement_population` source role;
- append-only evidence identity.

PostgreSQL enforces that a source snapshot belongs to the same tenant, legal entity, accounting book, expected fiscal period, and reporting currency as the report run. A source snapshot generated after the database-owned knowledge cutoff is rejected. Both tables use forced row-level security bound to `accounting_core.current_tenant_account_id()` and revoke public privileges.

The insert trigger overwrites caller-supplied reporting currency, period status, observation cutoff, and initial run status with database-derived values. There is intentionally no `source_bound`, `validated`, `approved`, `filing_ready`, or `published` state in this slice. A later owner command must define the transition from collected evidence to a complete report source package and must prove the required source population before any stronger status is introduced.

## Alternatives rejected

### Treat a report proposal hash as source authority

Rejected because a caller can hash an internally consistent package for an entity, currency, period, or snapshot that AIS never recorded.

### Copy all statement facts into the source registry

Rejected because that creates another accounting truth store and duplicates the retained trial-balance population. The registry references authoritative source evidence; derived report facts remain artifacts.

### Add validation, maker-checker, and publication tables now

Rejected because source authority, taxonomy validation, approval, publication, and regulator submission are different bounded responsibilities. Combining them would make a source record appear stronger than the implemented controls justify.

### Reuse reconciliation migrations or tables

Rejected because bank-reconciliation evidence and financial-report source evidence have different domain meaning and lifecycle. The only shared dependency is existing AIS accounting scope and retained snapshot evidence.

## Consequences

Positive consequences:

- a later report command can distinguish AIS-retained source evidence from arbitrary caller packages;
- tenant/entity/book/period/currency substitution fails at the database boundary;
- the observation cutoff is not caller-asserted;
- report-source evidence is append-only and independently auditable;
- no new publication or compliance claim is created.

Costs and limitations:

- migration 0020 must be restacked after reconciliation migrations 0015–0019 when those land;
- the current trial-balance snapshot remains the retained numerical source, so disclosure completeness and taxonomy mapping are still separate work;
- this slice does not yet create the authenticated application command that assembles and finalizes the complete source set;
- official IFRS/DART profiles, independent XBRL validation, accessible renderers, verified commentary, maker-checker, publication receipts, supersession/withdrawal, and recovery remain in Issue #51.

## Verification requirements

Before this ADR can move beyond Proposed, the exact integrated head must prove:

1. clean PostgreSQL 18 installation including migration 0020;
2. forced-RLS cross-tenant denial for both new tables;
3. rejection of a snapshot from another entity, book, period, or currency;
4. rejection of a snapshot newer than the database-owned cutoff;
5. caller-supplied currency, period status, cutoff, and initial run status cannot survive insertion;
6. source UPDATE/DELETE fails closed;
7. the public migration installer fails closed if migration 0020 is absent or fails;
8. full repository statement and branch coverage remain 100%;
9. current-head security/package gates and independent review pass.

Until those conditions are present on one exact head, the ADR remains Proposed and the PR remains Draft.
