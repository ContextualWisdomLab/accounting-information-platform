If the outbox row is missing, do not invent one—accept the proposal, reverse, or close, then retry the outbox publish. POST `/outbox-events` is not supported; GET the unpublished list, then retry. GET on the publish path is not supported; POST the publish, then retry. Default `page_limit` is 50 and the maximum is 100; pass `next_cursor` back as query `cursor` (`created_at|outbox_event_id`). An empty history returns `{"audit_events":[],"next_cursor":null,...}`—do not treat that as missing. The read writes zero rows and never sets `published_at`. If the header does not match this process, do not read—send the audit-event read to that tenant's AIS endpoint, then retry. If posting is rejected, the receipt is not written; create the named catalog or mapping row, or open the fiscal period, then retry. Do not invent chart-account codes in Billing or in the operator request. If close is rejected, restore the named catalog or snapshot row, then retry the close. Replay of the same Billing idempotency key returns the original receipt. Re-soft-close returns the same receipt (`snapshot_record_id` empty) and writes no second close event. Hard-close posts one AIS closing journal (`urn:cwl:accounting:general_journal:period_closing:{period_code}`) that zeros revenue and expense into `310100`, snapshots the live book once, and rejects posts and reversals; re-hard-close replays that snapshot and does not post a second closing journal. Ordinary Billing proposals cannot use `retained_earnings`—post revenue and expense, then hard-close. `hard_closed` cannot be soft-closed here—open a later period, then retry. ## Initial service objectives

- Proposal intake preserves every accepted source hash and idempotency decision.
- Posting and outbox publication are atomic.
- Trial-balance totals tie exactly to the selected journal population.
- No ordinary posting enters a soft-closed or hard-closed period.
- Soft-close changes `period_status_code` without a trial-balance snapshot or closing journal and still accepts AIS-owned `POST /journals` adjusting entries; hard-close posts AIS closing entries into `retained_earnings` 310100, then persists the snapshot in the same transaction that locks the period.
- Every receipt is traceable to policy, rule, mapping, fiscal period, journal, and source proposal versions.

## Telemetry

Record OpenTelemetry-compatible traces and metrics for proposal validation, idempotent replay, policy resolution, hold and rejection reason, posting latency, outbox lag, reversal, period close, and trial-balance generation. Never place account secrets, raw PII, or complete source payloads in telemetry.

## Recovery

- PostgreSQL point-in-time recovery and object-store versioning.
- Periodic restore rehearsal into an isolated environment.
- Journal and receipt hash reconciliation after restore.
- Outbox replay by event identity without duplicate posting.
- No recovery procedure rewrites a posted journal; corrections retain reversal lineage.

## Incident response

High-severity events include duplicate posting, unbalanced persisted journal, cross-tenant access, closed-period posting, missing source lineage, trial-balance mismatch, or receipt without committed journal. The immediate action is to stop the affected posting route, preserve evidence, reconcile the population, and issue explicit reversals or compensating entries after controller approval.
