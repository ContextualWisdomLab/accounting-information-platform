# Operability Baseline

## Persistence adapter

Set `ACCOUNTING_DATABASE_URL` to a PostgreSQL 18 database, apply `database/migrations/0001_accounting_foundation.sql`, then post and close through `PostgresPostingLedger` or `accept_journal_proposal`. For HTTP, set `ACCOUNTING_TENANT_REFERENCE` and bind `0.0.0.0:$PORT` with `run_journal_proposal_server`. POST `/journal-proposals` with `X-CWL-Tenant-Reference` only; that header scopes tenant identity and is not a general credential. If the header or payload tenant does not match this process, do not post—send the proposal to that tenant's AIS endpoint, then retry. After a receipt is posted, GET `/posting-receipts?idempotency_key=` with the same tenant header to read the persisted `accounting_posting_receipt`. If the header does not match this process, do not look up—send the lookup to that tenant's AIS endpoint, then retry. If no receipt exists for that Billing key, do not invent one—accept the proposal, then retry the receipt read. Ingest Billing JSON through `ingest_journal_proposal`; if the payload is a Billing operational reject or `proposal_status` is `draft` or `rejected`, do not ingest it—ask Billing for a `validated` proposal, then retry. Post that proposal with `post_proposal` so AIS resolves chart accounts from `account_role_mapping`. If posting is rejected, the receipt is not written; create the named catalog or mapping row, or open the fiscal period, then retry. Do not invent chart-account codes in Billing or in the operator request. If close is rejected, restore the named catalog or snapshot row, then retry the close. Re-closing a hard-closed period replays the existing snapshot and writes no second close event. After AIS emits `posting_receipt`, do not expect Billing to flip the proposal to `posted`. Replay of the same Billing idempotency key returns the original receipt. A Billing #17 credit adjustment uses `{tenant}:credit_adjustment:{credit_adjustment_id}:{source_payload_hash}:v{contract_version}` on the same POST `/journal-proposals`, GET `/posting-receipts`, and POST `/billing-proposal-pulls` path as invoice and cash; debit `usage_revenue` and credit `accounts_receivable` map to 410100 and 110100. Do not add a credit-specific route or account role. A Billing #20 taxed credit uses that same `credit_adjustment` key. Post the exact Billing lines: debit `usage_revenue` (tax-exclusive) maps to 410100, debit `tax_payable` (tax amount) maps to 210100, and credit `accounts_receivable` (inclusive) maps to 110100. Untaxed credits remain two-line revenue debit / AR credit. Do not invent a `tax_receivable` role or recompute `credit_tax_amount`. A Billing #19 taxed invoice uses the same `{tenant}:invoice_draft:{invoice_draft_id}:{source_payload_hash}:v{version}` key; debit `accounts_receivable` (tax-inclusive) maps to 110100, credit `usage_revenue` (tax-exclusive) maps to 410100, and credit `tax_payable` maps to 210100. Untaxed invoices remain two-line AR/revenue. Do not invent a `tax_` key or chart code. After AIS emits `posting_receipt`, do not flip Billing `proposal_status`. POST `/fiscal-periods` with the same tenant header, `legal_entity_reference`, `fiscal_period_reference`, and (for a new row) `period_start_date` plus `period_end_date` to insert or replay an `open` `fiscal_period` on the tenant calendar. Replay of an already-open period returns the same receipt and writes no second row. If the period is `hard_closed` or `soft_closed`, do not reopen it—open a later period, then retry the period open. GET `/fiscal-periods?legal_entity_reference=&fiscal_period_reference=` to read the existing period status and dates. If the header does not match this process, do not open or read—send the request to that tenant's AIS endpoint, then retry. If the period is missing, do not invent one—supply the `fiscal_period` dates on POST, or create the named catalog row, then retry the period read. POST `/period-closes` with the same tenant header to snapshot the book and set `soft_closed` or `hard_closed`; replay returns the same close receipt and writes no second snapshot. A period opened over HTTP can be closed on `POST /period-closes`. If close is rejected, restore the named catalog or snapshot row, then retry the close. GET `/trial-balances?legal_entity_reference=&book_reference=&fiscal_period_reference=` to read locked snapshot totals for a closed period or live aggregation for an open period. If the header does not match this process, do not close or read—send the request to that tenant's AIS endpoint, then retry. If the book or period is missing, do not invent balances—create the named catalog row, then retry the trial-balance read. GET `/account-role-mappings?legal_entity_reference=&book_reference=` with the same tenant header to read the existing catalog rows that map Billing semantic roles to statutory chart accounts (`cash_receipt` 110200, `accounts_receivable` 110100, `usage_revenue` 410100, `tax_payable` 210100) plus the stored `accounting_policy_version` and `posting_rule_version`. The read writes zero rows. If the header does not match this process, do not read—send the mapping read to that tenant's AIS endpoint, then retry. If the legal entity, book, or mapping row is missing, do not invent a mapping—create the named catalog row, then retry the mapping read. POST `/account-role-mappings` is not supported; GET the catalog mappings, then retry. GET `/journals?legal_entity_reference=&fiscal_period_reference=&book_reference=` with the same tenant header to list existing posted and reversing `general_journal` rows for that tenant, entity, book, and period. Each item is `journal_reference`, `idempotency_key`, `journal_status_code`, `accounting_date`, `line_count`, and `reversal_of_journal_reference`. Default `page_limit` is 50 and the maximum is 100; pass `next_cursor` back as query `cursor` (`accounting_date|journal_reference`). An empty period returns `{"journals":[],"next_cursor":null,...}`—do not treat that as missing. If the legal entity, book, or period is missing, do not invent journals—create the named catalog row, then retry the journal list. GET `/journals?idempotency_key=` or GET `/journals?journal_reference=` with the same tenant header to read the persisted posted journal and its lines. The posting receipt remains a header; this inquiry returns `chart_account_code`, exact decimal `debit_amount` / `credit_amount`, and `line_number` from existing `general_journal` and `journal_entry_line` rows. If the key or reference identifies a reversing journal, return that reversing journal—do not hide it. GET with the original Billing key still returns the original journal after a reverse. The read writes zero rows. If the header does not match this process, do not read—send the journal read to that tenant's AIS endpoint, then retry. If the journal is missing, do not invent one—accept the proposal, then retry the journal read. POST `/journals` is not supported; GET the posted journal, then retry. GET `/healthz` is an ops probe and returns `{"status":"ok"}` without a tenant header or accounting data. Set `BILLING_BASE_URL` to the Billing origin; do not hardcode a host. POST `/billing-proposal-pulls` with the same tenant header and optional `billing_base_url`, inclusive `proposed_after`, query `cursor`, and `page_limit` (default 50, maximum 100) to pull Billing `GET /v1/journal-proposals` pages (`proposal_status=validated` only). The list body is only `journal_proposals` plus `next_cursor`; pass `next_cursor` back as query `cursor`. Do not read body `items` or body `cursor`. GET-by-id returns one published proposal object with no envelope. Then post each validated item. If `BILLING_BASE_URL` is missing or Billing returns 422 or 5xx, do not write AIS rows—set the Billing origin or ask Billing to correct the tenant header and `tenant_reference` query, then retry the pull. A Billing 404 on `GET /v1/journal-proposals/{proposal_id}` is unknown or cross-tenant; do not retry as another tenant. After AIS emits `posting_receipt`, do not call Billing to mark the proposal `exported`, `posted`, or consumed. Replay of the same Billing page returns the original receipts and writes no second journal. POST `/journal-reversals` with the same tenant header, `tenant_reference`, `reversal_date`, `reversal_reason_code`, and either `journal_reference` or the original Billing `idempotency_key` to append an equal-and-opposite reversing journal. The response is the reversing `accounting_posting_receipt` (`posting_status_code` is `posted` for that reversing journal). GET `/posting-receipts?idempotency_key=` with the original Billing key still returns the original posted receipt. The reversing receipt is looked up with `idempotency_key=reversal:{journal_reference}`. Replay of the same reverse returns that receipt and writes no second journal. If the journal or key is missing, or the fiscal period is closed, do not invent a reversal—supply a posted journal in an open period, then retry. GET `/journal-reversals` is not supported; POST the reverse command, then retry.

## Initial service objectives

- Proposal intake preserves every accepted source hash and idempotency decision.
- Posting and outbox publication are atomic.
- Trial-balance totals tie exactly to the selected journal population.
- No ordinary posting enters a soft-closed or hard-closed period.
- Period close persists a trial-balance snapshot for the book and period in the same transaction that changes `period_status_code`.
- Every receipt is traceable to policy, rule, mapping, fiscal period, journal, and source proposal versions.

## Telemetry

Record OpenTelemetry-compatible traces and metrics for proposal validation, idempotent replay, policy resolution, hold and rejection reason, posting latency, outbox lag, reversal, period close, and trial-balance generation. Never place account secrets, raw PII, or complete source payloads in telemetry.

## Recovery

- PostgreSQL point-in-time recovery and object-store versioning.
- Periodic restore rehearsal into an isolated environment.
- Journal and receipt hash reconciliation after restore.
- Outbox replay by event identity without duplicate posting.
- No recovery procedure rewrites a posted journal; corrections retain reversal lineage.

## Incident response

High-severity events include duplicate posting, unbalanced persisted journal, cross-tenant access, closed-period posting, missing source lineage, trial-balance mismatch, or receipt without committed journal. The immediate action is to stop the affected posting route, preserve evidence, reconcile the population, and issue explicit reversals or compensating entries after controller approval.
